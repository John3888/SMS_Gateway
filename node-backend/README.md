# Node SMS backend — no database

A standalone Express + WebSocket backend for the ESP32 gateway. Each API call returns JSON. Jobs, rate counters, request keys and recent results exist **only in memory**. No SMS data is written to disk and no database service is required.

```text
Applications → HTTP API → in-memory queue ←→ WebSocket → ESP32 → A7670E → SMS
```

## Run

Use Node.js 22.13+ and run these commands from this folder:

```sh
npm ci --include=dev
npm run setup
npm run build
npm start
```

Setup creates missing configuration files with separate random device/application keys and validates existing settings. Existing files and credentials are never overwritten. If `.env` already exists but its application-key file is missing, rerun `npm run setup` to create that file while preserving the device key. Inline `APP_KEYS` JSON is also supported; otherwise `APP_KEYS_FILE` selects the key file (default `./app-keys.json`). These files contain credentials/settings, not a message database. `app-keys.example.json` shows the format. Restart after changing settings. Keep application IDs stable when rotating their keys.

The default local listener is `http://127.0.0.1:3000`. Development with automatic restart: `npm run dev`. Restarting also clears all in-memory jobs, history, quotas and deduplication keys.

## Project structure

The backend follows the TripTIcket backend's TypeScript/ES module conventions: central server, routes and realtime files, shared configuration and middleware, and feature modules with routes, controllers, services, validation and types.

```text
node-backend/
  src/
    server.ts              # Environment loading, startup and shutdown
    app.ts                 # Testable HTTP server and service composition
    routes.ts              # Central route registration
    realtime.ts            # ESP32 WebSocket lifecycle and heartbeat
    config/                # Environment and configuration validation
    middlewares/           # Authentication, validation, limits and errors
    modules/
      sms/                 # SMS API, queue, scheduling and responses
      device/              # Device protocol, validation and health
    types/                 # Shared configuration and Express types
  scripts/setup.ts         # Generate initial credentials
  dist/                    # Generated by npm run build; do not edit
```

Use `npm run dev` while editing. For deployment, install dependencies, run `npm run build`, then `npm start`. The build outputs `dist/src/server.js`; rebuild after source changes. `.env` and `app-keys.json` remain in the backend root. The API routes, JSON responses, WebSocket protocol and in-memory behavior are unchanged by this restructuring.

Deploy the `node-backend` folder to your VPS and run one Node process under your service manager with automatic startup/restart. Set its working directory to this folder so `.env` and `app-keys.json` resolve correctly. Keep `HOST=127.0.0.1` when the reverse proxy runs on the same VPS. Your reverse proxy should expose HTTPS/WSS on public port 443 and forward HTTP plus WebSocket upgrades to Node's internal port (3000 by default), with an idle timeout longer than the 30-second heartbeat. No persistent message storage is needed.

Install build dependencies with `npm ci --include=dev`, build with `npm run build`, and start with `npm start`. Run `npm run setup` only on a new installation; preserve existing credentials on subsequent deployments. Local `node_modules` and `dist` are omitted from the source folder and regenerated on the VPS. Configuration templates and the setup script are retained because they are needed to configure a new server.

## ESP32 connection

In the Arduino sketch's `gateway_config.h`:

```cpp
constexpr bool CLOUD_ENABLED = true;
constexpr char CLOUD_HOST[] = "gateway.your-domain.com";
constexpr uint16_t CLOUD_PORT = 443;
constexpr char CLOUD_WS_PATH[] = "/device/ws";
constexpr char CLOUD_DEVICE_KEY[] = "YOUR_BACKENDS_DEVICE_KEY_VALUE";
```

Use the actual hosted domain without `https://` or a path, and the exact `DEVICE_KEY` from your backend settings. Supply the trusted `CLOUD_ROOT_CA` for its TLS certificate chain. See the [Arduino guide](../arduino/README.md). The `CLOUD_` setting names simply mean the remote backend; no particular hosting provider is required.

The ESP32 initiates one authenticated **standard WebSocket** connection at boot and reconnects after interruptions. Its protocol path is `/device/ws`, not `/socket.io/`. Another connection with the valid device key replaces the previous one. Applications call the HTTP API rather than opening sockets to the ESP32 themselves.

## Send an SMS

Keep this application's key in your existing application's backend. Use a different application key for each application.

```http
POST https://gateway.your-domain.com/sms-send/
Authorization: Bearer YOUR_APPLICATION_KEY
Idempotency-Key: notification-001
Content-Type: application/json

{
  "number": "+639171234567",
  "message": "Hello from my application!"
}
```

This immediately returns HTTP 200 with the existing response format and a job status:

```json
{
  "success": true,
  "message": "SMS job sent to gateway.",
  "data": { "number": "+639171234567", "message": "Hello from my application!" },
  "job": {
    "id": "server-generated-uuid",
    "idempotency_key": "notification-001",
    "status": "queued",
    "status_url": "/api/v1/sms/server-generated-uuid",
    "created_at": 1793793600000,
    "expires_at": 1793797200000
  }
}
```

Acceptance is not proof of transmission or handset delivery. Use the returned status URL to check the retained in-memory result, or use the bounded-wait option below.

### Return the ESP32 result to the same API call

Add optional `wait_ms` (0-30000):

```json
{
  "number": "+639171234567",
  "message": "Hello from my application!",
  "idempotency_key": "notification-001",
  "wait_ms": 20000
}
```

The request waits up to 20 seconds for this job's result:

| HTTP status | Meaning when waiting                                                                 |
| ----------- | ------------------------------------------------------------------------------------ |
| 200         | Modem confirmed submission; `job.status` is `submitted`                              |
| 202         | Still queued/sending after the wait; `pending: true` and the status URL are returned |
| 502         | Modem/preflight failure; `job.status` is `failed`                                    |
| 504         | Send outcome unknown; inspect before retrying                                        |
| 409 / 410   | Job was cancelled / expired while waiting                                            |

`wait_ms=0` is the default immediate-response behavior. A timeout does not cancel the job or mean it was not sent. Set client/proxy timeouts longer than `wait_ms`. At most 100 API calls may wait at once; additional waiting calls receive 429. Your application backend should forward the request and preserve the returned HTTP status, JSON and `Retry-After` header.

## API routes

| Method/path                       | Purpose                                                                  |
| --------------------------------- | ------------------------------------------------------------------------ |
| `POST /sms-send/`                 | Existing `{ number, message }` request                                   |
| `POST /api/sms-send/`             | Alias for an application's `/api` prefix                                 |
| `POST /api/v1/sms`                | Canonical `{ phone, message, idempotency_key }`; 202 for new queued work |
| `GET /api/v1/sms/<id>`            | Own application's retained job/result                                    |
| `GET /api/v1/sms?page=0&limit=20` | Own retained results/pending jobs; limit 1-50                            |
| `DELETE /api/v1/sms/<id>`         | Cancel only while queued                                                 |
| `GET /api/v1/health`              | Own pending count, memory mode and device connection/readiness           |
| `GET /healthz`                    | Process health; no application key required                              |

All other HTTP API routes require the application's bearer key. The ESP32 uses the separate `DEVICE_KEY` for its WebSocket handshake. Both trailing-slash forms work. Job IDs/status URLs are server-generated; another application's records return 404. The readiness value is a recent device report, not a guarantee that the next SMS will succeed.

Numbers must be international `+countrycode...` strings. Messages support 1-70 BMP characters; multipart messages and non-BMP emoji are unsupported. Optional `ttl_seconds` (60-86400; default 3600) limits time waiting queued. Claimed/sending work is never automatically reassigned or expired.

For retries, use the same `Idempotency-Key` header or `idempotency_key` field and identical phone, text and TTL. If both key locations are supplied they must match. The compatibility routes generate a key when absent; then every separate POST is a new job. The canonical route requires a key. Keys are 1-64 ASCII letters, digits, hyphens or underscores. Changing `wait_ms` does not change the SMS identity.

## Memory bounds and limits

| Control                             | Default                                    |
| ----------------------------------- | ------------------------------------------ |
| Each application's new SMS requests | 10/minute, burst 5                         |
| Each application's daily admissions | 200, reset at 00:00 UTC or process restart |
| Each application's pending jobs     | 20                                         |
| Total pending jobs                  | 100                                        |
| Gateway-wide admissions             | 12/minute, burst 10                        |
| Each application's HTTP requests    | 120/minute, burst 30                       |
| Retained completed records          | 200 total, at most 15 minutes              |
| Physical sending                    | One job, minimum five-second device pause  |

Per-app limits are in `app-keys.json`/`APP_KEYS`. Global limits, `MAX_COMPLETED` and `HISTORY_TTL_SECONDS` are configured in `.env`. Rate buckets allow short bursts followed by gradual refill. Waiting applications take turns, with FIFO within each application. Quotas count accepted jobs even if later cancelled, failed or expired. All counters are process-local; run **one backend process/replica** for the gateway.

Overload returns 429 and `Retry-After` in seconds. Wait before retrying with the same key. Device messages are limited separately to 240/minute with burst 30. Application keys never authorize the device connection. Browser frontends should call your authenticated application backend so gateway keys stay private.

## Restart behavior

**Pending jobs, history, deduplication keys and rate counters are lost on every restart.** A retry after restart or result eviction can send another SMS. Inspect uncertain sends before issuing another request. Retained completed records are pruned by age/count; active jobs are not evicted to make room.

The ESP32 still keeps its own submission record in NVS. If it reports an old result after the backend has restarted/forgotten that job, the backend acknowledges `unknown` with `forgotten: true` to release the stale device record. It does not recreate or resend the old SMS and does not claim successful delivery. Your application will get 404 for that forgotten status URL. A device restart during an armed send can still require the firmware's manual quarantine recovery.

The only files read/written by setup are credentials/configuration. The running backend writes no message database or history file. Existing private `.env` and Arduino credentials are preserved; obsolete settings such as an old `DB_PATH` are ignored and may be removed from your own configuration.
